AUTO-706 next phase (as of 2026-06-15, branch `nil/auto-706-onprem-logs-to-dd`): adopt **wide events / canonical log lines** (loggingsucks.com / observability 2.0) for IDI.

**Vision (aligned with user):** the unit of work is a *phone call*; emit **one wide canonical event per service hop** — voice-agent, cloud workflow (`call.finished` already IS this), and the on-prem Radiant activity hop (the gap / "island"). Correlate hops by a shared key. Aggregate metrics at query time from the wide events; only true infra signals (Temporal SDK worker health like `schedule_to_start`, DD host metrics) stay as real metrics. **No head-sampling** — low volume (~5 calls/hr, one clinic), every healthcare call matters; if cost ever bites, use DD-side conditional retention (keep all anomalous, sample only clean happy-path), never app-side random drop.

**Backend decision:** conform to **Datadog**, not a parallel OTel stack. Cloud "traces" are ddtrace wearing an OTel-API hat (Temporal's `TracingInterceptor` only speaks OTel) → DD agent. The real OTel collector is the pho/Azure BU's, not this stack. On-prem ships logs via the DD Windows Agent (shared ingestion key — see below). Wide events ride the log pipeline, so NO second OTel path needed on-prem (this also routed around the risky ddtrace↔OTLP trace-stitch).

**Correlation key (resolved 2026-06-15):** the **LiveKit session id (`room.sid`)** — PHI-free, and it also fetches LK audio/transcripts. No separate uuid4: `room.sid` is the single canonical call id doing correlation + DD replacement for room_name + LK link ([[idi-call-id-is-phi]]). Propagated to on-prem via a **Temporal header propagator** (set-once cloud-side, read-everywhere via an interceptor on the on-prem Worker — which today has NONE). On-prem Radiant activity input models do NOT carry any call id today, and the on-prem activity only sees the child `{parent}-book` workflow id — hence the propagator. On-prem emits **per-operation** wide events (one per Radiant SOAP call: op, PHI-safe arg shape, latency, SOAP status, outcome, error class, + session_id); aggregate per-call at query time.

**Scope grew (resolved 2026-06-15):** DD is NOT PHI-permitted, so a **leak-fix workstream** is now in scope and sequenced FIRST as its own PR: scrub `room_name`/`call_id` from all DD-bound cloud logs (`voice_worker.py`, `voice_agent.py`) + re-key `call.finished` onto `session_id` + update dashboard widgets querying `@call_id`. It's a live compliance fix AND establishes `session_id` as the id the wide-events stack builds on. Both prior open gating questions are now resolved.
